Most important Effect takeaways for implementation
- Use Effect.fn around operational methods for traceability.
- Keep orchestration in Effect.gen with explicit error boundaries.
- Model recoverable external failures as typed errors and continue where appropriate.
- Keep dependency wiring in layers; provide once at program boundary.
- Use config/schema patterns for script options and environment integration.

Resend SDK research (batching question)
- Checked installed SDK types in packages/core/node_modules/resend/dist/index.d.mts.
- Resend does expose batch APIs (batch.send/create), so batching is possible in theory.
- For this MVP, current design is per-subscription send via Notifier.send(user, events), so sequential one-by-one processing is the best fit.

Clarified operational behavior
- Use Effect concurrency/reliability patterns up to external boundary.
- For outbound email failures (Resend/API/network):
  - log as errors
  - do not crash entire run because of one failed email
  - rely on provider retry policy for transient failures

Planned notify flow (issue 05)
1) Load users and subscriptions.
2) Filter to enabled subscriptions.
3) For each subscription (sequential):
   - Resolve user (fatal if missing).
   - If schedule is relative: log skip and continue.
   - Evaluate due with isDue.
   - Apply dedupe guard isAlreadySentToday.
   - Call Subscriptions.check for local-date match.
   - If events found:
     - dry-run: log intent only
     - normal mode: call Notifier.send
     - on successful real send: update subscription.lastSentAt
4) Emit summary logging.
5) Exit behavior:
   - fatal integrity/setup errors abort run
   - per-subscription external send errors are logged and processing continues
